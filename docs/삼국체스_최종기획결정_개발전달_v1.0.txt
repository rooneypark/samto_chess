작성일: 2026-11-13 (한국 시간)

0. 작업 범위와 금지 사항
- 이번 전달 준비에서는 문서만 정리한다. 기능 개발은 다음 담당자가 수행한다.
- Git add/commit/push, 저장소 생성·초기화·원격 변경을 하지 않는다. 사용자가 새 저장소를 만들 예정이다.
- 기존 game/, docs/, reference/와 저장 데이터를 삭제하거나 덮어써 초기화하지 않는다.
- 전달된 작업 목록의 “game 폴더 git 커밋”은 삭제한다. 향후 Git 작업은 사용자 별도 지시가 있을 때만 한다.
- 이 파일을 최종 명세의 단일 진입점으로 삼는다. 서로 다른 버전의 UI·수치를 임의로 혼합하지 않는다.

1. 기획 결정 D1~D8
D1 게임 이름: 삼국체스.
  타이틀·화면·새 문서는 삼국체스로 통일한다. 원본 분석 문서의 제목은 역사 기록이므로 수정하지 않는다.
D2 하단 탭: 상점 / 병영 / 성문 / 동맹 / 군웅대전.
  상점=장수·보물 모집과 상품 구매. 병영=장수 성장·편성·보물함.
  성문=중앙 대기·전역 선택·출정. 내정은 군주 정보 또는 성문 내부 진입점에 둔다.
  전역·모집·내정을 별도 하단 탭으로 만들지 않는다.
D3 홈 장수: 성문 앞에 현재 편성 장수 6명을 배치한다.
  승인된 픽셀 시안을 유지한다. 인물 포스터로 배경을 대체하지 않는다.
  “홈 장수 금지”로 해석되는 명세 항목은 이 결정으로 대체한다.
D4 성급별 전법: 대표 액티브 1개 + 영구 각성에 따른 강화/변형(안 A).
  영구 각성 3성·5성에서 기존 전법의 계수·지속시간·부가효과를 강화한다.
  현재 장수별 정의를 기준으로 강화값을 데이터화하고 미리보기를 제공한다.
  액티브 3개, 별도 마나통 3개, 스킬 선택 버튼은 P0에 추가하지 않는다.
  전투 중 합성 등급과 영구 각성 별은 별개의 성장축이다.
D5 능력치 배율: 전투 합성 등급 I~V에 1.6^(n-1).
  배율: 1 / 1.6 / 2.56 / 4.096 / 6.5536. 계산 중 임의 반올림 금지, 최종 능력치에서 내림.
  HP/공격/방어/마법방어에만 적용. 사거리·마나·공격주기·이동시간에는 적용하지 않는다.
  영구 레벨·각성은 기존 신규 게임 공식 (1 + .03*(level-1) + .08*(star-1))을 유지한다.
  제시된 “원작 1/1.6/2.6/3.6”은 채택하지 않는다. 현재 V등급 체계와도 항목 수가 다르다.
D6 C등급 모집: 즉시 개방 유지.
  의용보병·의용궁병·군영참모의 검증된 원본 자산을 사용한다.
  C/B/A/S=60/30/8/2%, 등급 내 균등. C 60%를 다른 등급으로 재분배하지 않는다.
  자산이 검증되지 않은 실명 장수는 풀에서 제외한다. 유효한 등급별 항목이 하나도 없으면 모집을 차단하고 원인을 표시한다.
D7 군웅대전: 양 진영 각각 자신의 군략을 적용한다.
  플레이어 군략을 상대 NPC에게 복사하는 동작은 버그로 수정한다.
  NPC 초기값: 청운(cloud)=책략, 솔바람(wind)=선봉, 백운(tiger)=선봉.
  상대 군략을 대전 시작 전 표시하고 매치 스냅샷에 고정한다.
  공정 보정: 양쪽 Lv10·영구 각성3·전투등급III·보물 미적용을 유지한다.
  P0는 로컬 NPC 대전이다. 온라인 이용자·서버 순위처럼 표시하지 않는다.
D8 저장 방식: IndexedDB 유지.
  현재 브라우저 저장이 이미 IndexedDB로 전환되었으므로 localStorage로 되돌리지 않는다.
  IndexedDB가 원본 저장이며 localStorage는 호환 미러, 테스트 어댑터, 이전 저장 이관 용도로만 사용한다.
  프로필·재화·보상·명령 영수증·원장은 같은 거래로 확정한다. 미러 쓰기 실패를 원본 저장 실패로 오인하지 않는다.
  다른 탭의 revision 충돌, 중복 명령, 실패 rollback, 재접속을 검증한다.

2. 전투·적 데이터 추가 결정
- 황건 첫 전투의 기준은 reference-v012/기존데이터_v010/stage-proposal.json을 채택한 game/stage-data.js이다.
- 첫 근접병: HP300 / ATK40 / DEF10 / MDEF5 / 사거리1 / 공격주기24tick / 마나0 / 전법 없음.
- 적 도사(mage): HP220 / ATK50 / DEF5 / MDEF20 / 사거리4 / 공격주기28tick / 마나0 / 전법 없음 / 기본 피해 physical.
- 도사 외형이라는 이유만으로 회복 전법을 추가하지 않는다. 이 적은 이번 황건 튜토리얼 전역에서는 원거리 일반 적이다.
- 회복형 적은 이후 별도 enemyDefId로 만들고 마나·전법·수치를 정의한다. 현재 mage를 몰래 변경하지 않는다.
- 보스와 모든 적 좌표는 stage-data의 라운드 데이터를 따른다. 보스는 (3,7).
- stage-data의 bossSkill, reward, victorySilver, equipmentReward까지 실제 실행 경로에서 읽게 한다.
- skillId가 있으면 무조건 boss로 치환하는 현 매핑을 제거하고, 명시적인 스킬 ID 레지스트리를 사용한다.
- 주유: 발사 후 +20/+40/+60/+80tick, 총4회, 즉시 피해 없음.
- 황충: 최장 맨해튼 거리 → HP비율 최저 → 인스턴스 ID 최저.
- 장료: 적 후열 → DEF 최저 → ID 최저. 아군/적 진영에 따라 후열 방향을 반전한다.
  인접 빈칸 선택은 시전자와 맨해튼 거리 → y → x. 예약 실패 시 현재 평타 표적에 200% 피해.
- 장판 5개 상한은 현재 구현된 지속 장판 범위의 규칙이다. 모든 회복·보호막·버프를 같은 전역 상한으로 뭉뚱그리지 않는다.

3. 시각·콘텐츠 고정 결정
- 승인된 픽셀 UI, 성문 앞 장수, 기존 메뉴와 다이얼로그 테두리를 유지한다.
- 최신 제작 기준: docs/캐릭터_원화_모션_스킬이펙트_통합가이드.md. 외형은 승인된 우리 게임 독립 원화, 동작은 촉한 실제 MOV/ATK/SPC 참조. 정면·후면·왼쪽3방향 제작, 오른쪽은 측면 반전. 신규 장수/효과 제작 요청은 이 기준을 따른다.
- 화·수·지·풍 등 모든 범위 효과는 영향받는 각 칸에 동일 클립을 복제한다. 기본은 동일 프레임 동시 재생이며, 사용자 최신 허용에 따라 지정 순서/지연의 순차 연출도 가능하다. 피해 판정 시점은 바꾸지 않는다.
- 한 이펙트의 가시 영역은 한 칸 안에 맞추며 칸 단위 clip을 적용한다. 범위 전체를 덮는 확대 이미지로 되돌리지 않는다.
- 초선: 대표 전법과 여포 인연은 채택. 원본 장수 바인딩 검증 후 플레이 가능 목록과 모집에 추가한다.
  타 인물 스프라이트를 근거 없이 초선으로 바꾸지 않는다. 미확인 자산은 대기 상태로 명시한다.
- P1 목표는 8전역 24전투. 현재 전달 데이터에서 제작 대기인 배치·대사·보상은 별도 콘텐츠 제작 작업이며, 이미 완성된 것으로 취급하지 않는다.
- 서버 PvP·실시간 동맹·실결제는 P2. P0 정리 작업에 끼워 넣지 않는다.

5. 현 상태 정정 (2026-11-13 소스 확인)
- 단위 테스트 선언은 42개다. 직전 실행에서 42/42 통과했다. 다음 담당자는 인수 시 다시 실행하고 실제 결과를 적는다.
- 튜토리얼 핵심 흐름, 임무, 우편, 보물 승급·분해는 이미 구현되어 있다. 현재 감사는 최신 구현 현황으로 통합되어 있다.
- IndexedDB 저장·명령 영수증·원장·탭 충돌 처리가 이미 있다. 신규 도입이 아니라 정합성·크기 관리 작업이다.
- 주유4회, 황충/장료 우선순위 수정, 장판5개 상한, rulesetId/contentVersion/seed/RNG/fixedDelta 헤더가 있다. 먼저 회귀 검증하고 부족한 부분만 수정한다.
- 현재 실제 적 수치와 좌표는 stage-data로 덮어쓴 결과를 쓴다. enemySpecs의 낡은 초기 리터럴 400/48만 보고 현재 적이 그 수치라고 보고하지 않는다.
- 도사 전법이 없는 것은 위 2절의 채택 결정이다. “꺼진 회복 스킬 복구” 작업으로 넘기지 않는다.
- 초선은 엔진 전법 규칙과 테스트만 있고 실사용 장수 카탈로그·자산 연결은 아직 없다.
- 신뢰할 최신 상태는 현재 소스·실행 결과다. v012-implementation-audit 문서도 이를 대신하는 증거가 아니다.

6. Claude 개발 작업 순서
단계 1: 인수·문서 정리 (Git 작업 없음)
  a. 작업 파일과 테스트를 확인하고 사용자의 기존 변경을 보존한다.
  b. docs/v012-implementation-audit.*를 소스와 대조하여 갱신한다. 사용자 요청으로 과거 감사와 중복 산출물은 제거하고 최신 현황으로 통합했다.
  c. 구현/부분/미구현/기획 미정/자산 대기/미검증을 구분한다. 단위 테스트 통과를 화면 전체 완료로 해석하지 않는다.
  d. game/SHOP.md, game/assets/ui/ASSETS.md의 낡은 전투 미연결 문구를 갱신한다.
  e. 이 결정서를 기준으로 각 데이터·화면의 추적표를 만든다.
단계 2: 데이터·저장·안전성
  a. stage-data의 보스 전법·보상·승리 은화·장비 보상을 단일 원천으로 연결한다.
  b. enemySpecs의 중복 리터럴과 waves 등 중복 선언을 정리한다. 원본 자산 매핑과 전투 수치 정의를 분리한다.
  c. NPC 고유 군략을 매치와 전투 양쪽 경로에 연결한다.
  d. run.profile은 허용 목록으로 생성한다. heroes/order/treasures/strategy/reducedMotion 등 실제 필요한 값만 복사한다.
     ledger/services/shop 영수증/battleReceipts/archivedRuns/이전 battleRun을 중첩 복제하지 않는다.
  e. 저장 키와 RULESET 참조를 상수로 통합한다. 이름·사용자 입력은 텍스트 노드 또는 escape 후 출력한다.
  f. 출정 중 보물 장착·해제도 금지한다. 승급·분해만 막아서는 안 된다.
  g. 원장·이벤트 dedupe·영수증 보관 정책을 설계한다. 활성 출정/미확인 보상/미수령 우편/재시도 가능 명령은 고정 보관한다.
     오래됐다는 이유로 영수증만 지워 중복 지급을 다시 허용하지 않는다. 상세 로그 압축, 완료 요약/거부 경계와 함께 관리한다.
     보관 한도 적용 전후 동일 보상 재요청·날짜 역행·새로고침에서 지급1회를 검증한다.
  h. progression의 legacy 분기는 저장 이관 경로와 테스트를 추적한 뒤 정리한다. 마이그레이션에 쓰는 코드까지 삭제하지 않는다.
  i. stun은 P0 검수의 취소 규칙과 연결되므로 무조건 제거하지 않는다. 어댑터로 유지·검증하거나 관련 계약 변경을 명시한다.
  j. 마법 클립은 화·수·지·풍 공통 라이브러리/뷰어에서 사용한다. 현재 장수에 바인딩되지 않았다는 이유만으로 삭제하지 않는다.
     menu-pressed 이미지도 코드·CSS·매니페스트·승인 시안 참조를 확인하고 실제 미사용 실행 자산만 정리한다. 원본 기획 증거는 보존한다.
단계 3: 테스트 환경과 P0 인수
  a. package.json 및 lockfile에 Playwright를 선언한다. 설치된 버전을 고정하고 테스트 명령을 제공한다.
  b. 브라우저 경로와 서버 URL을 환경설정으로 뺀다. reference 내부 node_modules나 고정된 Windows Edge 경로에 의존하지 않는다.
  c. 고립된 저장 프로필과 IndexedDB를 사용하고 저장 완료 ACK를 기다린다. 임의 sleep이나 localStorage만 조작하는 fixture에 의존하지 않는다.
  d. 이미 구현된 전법/스택/리플레이 규칙은 회귀 검수한다. 초선은 검증된 자산 확보 후 카탈로그·상점·편성·전투까지 연결한다.
  e. 화면별 LOADING/EMPTY/LOCKED/ERROR/COMMITTING 및 재시도·뒤로가기·입력 취소·키보드를 검수하고 빠진 상태를 보완한다.
  f. 튜토리얼 시작부터 영구 훈련, 보상 중복 방지, 중도 종료/재개, 실패 상태까지 인수한다.
단계 4: P1 콘텐츠 (P0 인수 후)
  a. 8전역24전투의 적 배치·대사·승패·해금·보상 데이터를 먼저 작성한다. 스테이지 ID별 검증과 플레이 테스트 후 연다.
  b. 내정 생산은 이미 일부 있다. 건설·승급 비용/해금, 토벌 소비·시간·보상·취소 정책을 먼저 데이터로 작성한다.
  c. 원본 책략 효과음·볼륨은 이미 있다. BGM과 기본 공격 음향을 별도로 연결하고 음소거/재생 정책을 검수한다.
